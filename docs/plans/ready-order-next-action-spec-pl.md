# Kolejność delegowania i widok „Następny ruch” — specyfikacja implementacyjna v1

**Status: wymaganie do wdrożenia, nie opis gotowej funkcji.** Adresat: agent implementujący `pi-herdr-subagents`. Słowa MUSI, NIE WOLNO i POZA ZAKRESEM są normatywne. Przy sprzeczności z aktualną ochroną sesji, gałęzi lub dostarczenia należy zatrzymać odpowiedni etap i zgłosić konflikt; nie osłabiać ochrony dla zaliczenia testu.

## 1. Rezultat i granice

1. Dla jawnie włączonego planu Pi rodzic ma otrzymać deterministyczną odpowiedź: które zadanie może teraz zlecić, co wstrzymuje inne, kto ma następny ruch. Kolejność planu to preferencja, nie bariera. Blokada A nie jest globalną pauzą.
2. Rozszerzenie **wylicza i egzekwuje dopuszczalność**, a **rodzic wywołuje** `plan_update` i `subagent`. Sam odczyt, refresh, timer, `/reload`, restart i nadejście wyniku NIE uruchamiają nowego koordynatora. Zachować istniejącą dostawę wyniku do rodzica. Nie obiecywać postępu bez aktywnego rodzica ani dokładnie jednokrotnego przetworzenia wiadomości przez model.
3. Zakres: zadania powiązane z jednym aktywnym planem sterowanym przez oryginalnego rodzica, łącznie z zasobami powierzonymi koordynatorowi dla jego dzieci. Bezpośredni worker dla prostego zadania jest dozwolony. Nie zmieniać semantyki niezwiązanych wywołań, historycznych planów ani obcych harnessów. Nie liczyć nieznanej sesji jako dowodu bezpieczeństwa.
4. Poza zakresem: autonomiczny `workflow_start`, nowy daemon, nowy transport, przekazanie władzy na fork, automatyczna akceptacja, merge/push, automatyczne tworzenie worktrees, odbieranie procesom praw systemowych, rozproszona blokada między niezależnymi instancjami Pi. Deklaracja zakresu pracy to kontrakt współpracy, **nie sandbox**.

## 3. Nowy kontrakt danych i sterowania

Wszystkie nazwy poniżej to **projektowane** rozszerzenia API. Metadane wykonawcze zapisywać przy istniejącym planie/próbie pod tą samą kontrolą wersji i właściciela. Nie zapisywać osobnej listy „ready”. Obecnych `TaskStatus` nie rozszerzać o stany UI. Zmiana formatu trwałego wymaga wersjonowania, czytania starego formatu bez nadawania uprawnień oraz odrzucenia nieznanej wersji bez nadpisania pliku.

| Nowa powierzchnia | Kontrakt v1 |
|---|---|

Pierwsze wywołanie włącza tryb `ready_order` dla planu; sugerowana wartość 1. Włączenie tylko bez istniejących prób (dla starego planu w toku użyć nowego planu, nie rekonstruować rezerwacji). ## 4. Algorytm decyzji i zabezpieczenie przed wyścigiem

**Dla pierwszego startu** kandydat jest gotowy wtedy i tylko wtedy, gdy: tryb włączony, nie ma pauzy, rodzic ma prawo wykonania, zadanie jest `pending`, wszystkie bezpośrednie zależności są aktualnie `accepted`, obszar jest zweryfikowany, nie ma konfliktu zasobu, liczba zajętych miejsc jest mniejsza od limitu, a stan zapisów pozwala bezpiecznie przydzielić miejsce. Brak zależności oznacza spełniony warunek. Jeżeli konsument wymaga zintegrowanego kodu, w v1 modelować **osobne zadanie integracji** z dowodem wersji dostępnej w docelowym środowisku; konsument zależy od niego, nie tylko od akceptacji patcha. Nie zgadywać integracji z obecności pliku.

Wyliczyć powody dla wszystkich zadań, wybrać pierwsze gotowe wg `plan.tasks` (kolejność zapisu, nie sortowanie po nazwie, czasie czy UUID). Widok nie rezerwuje miejsca. Tabela definiuje główny komunikat; awaria całego odczytu = diagnostyka, nigdy gotowa lista. Dla zadania pokazać także wtórne przeszkody; nie maskować niepewnej rezerwacji statusem końcowym.

| Warunek | `state` / `owner` / `action` |
|---|---|
| Niepewna dyspozycja, tożsamość lub zwolnienie dotyczy tej próby | `uncertain / parent / inspect_recovery` |
| `accepted`, `cancelled`, `skipped`, bez nierozliczonej rezerwacji | `closed / none / none` |
| `in_review` albo nowa propozycja wyniku do oceny | `review / parent / inspect_result` (jawna aktualna blokada ma pierwszeństwo przed starszą propozycją) |
| `blocked` lub `failed` | `decision / user lub parent / resolve_blocker`; bez strukturalnych danych domyślnie rodzic |
| `in_progress` z utworzoną próbą, ale potwierdzonym brakiem dispatch | `assigned / parent / dispatch_bound` (jeśli pauza: `wait / parent / continue_plan`) |
| `in_progress` z nadzorowanym wykonaniem, w tym koordynator czekający na swoje dzieci | `working / coordinator / await_result`; przy bezpośrednim workerze owner=`runtime` (oczekujemy zdarzenia) |
| `pending`, zależność `failed/skipped/cancelled` | `decision / parent / revise_or_skip`; nie czekać bezterminowo na wynik. Rodzic może też jawnie przywrócić zależność. |
| `pending`, pozostała niezaakceptowana zależność | `wait / parent / await_dependency`, wymienić ID |
| `pending`, pauza / brak obszaru / konflikt obszaru / wyczerpany limit | Odpowiednio `wait / parent / continue_plan`, `decision / parent / set_work_area`, `wait / runtime / await_resource`, `wait / runtime / await_capacity` (priorytet wg kolejności w tej komórce). |
| `pending` i komplet warunków | `ready / parent / start_attempt` |

**Transakcja:** sprawdzić warunki przy `attempt(start)` i zarezerwować miejsce i obszar razem z próbą. Przy `retry` wymagane te same bramki poza statusem początkowym; retry jest odrębną decyzją, nigdy automatycznym wyborem z listy ready. Przy `subagent(planTask)` sprawdzić je ponownie bez naliczania własnej rezerwacji drugi raz. Uruchomienie tylko dla pasującej rezerwacji, `cwd`, bieżącej próby i pierwotnej władzy. Jeśli dwie decyzje widziały ostatnie wolne miejsce, najwyżej jedna może przejść do transportu. Kontrola musi obejmować także ścieżkę wznowienia: nie pozwolić uruchomić nowej pracy w zwolnionym obszarze bez jego ponownego przydziału. Ponowienie naprawy u tego samego workera nie tworzy drugiego miejsca koordynatora. Nie używać niepowiązanego spawnu jako obejścia odmowy dla tego samego zadania.

**Zasoby:** jeden slot to jedno drzewo wykonawcze powiązanego zadania, a nie każdy panel. Dzieci pracują w przydziale rodzica; ich praca nie może rozszerzyć obszaru ani trybu. Dwa odczyty mogą współistnieć, zapis wyklucza zarówno drugi zapis, jak i odczyt z tego samego obszaru. Aktualny właściciel nie może traktować otwartej sesji z ręcznym wejściem jako środowiska oddanego do wyłącznego zapisu. Niezarządzana lub ręczna zmiana jest poza gwarancją blokady; przy zaobserwowanej rozbieżności nie integrować ani nie nadpisywać zmian użytkownika.

**Zwolnienie:** tylko potwierdzony brak dispatch albo potwierdzone zakończenie wszystkich powiązanych wykonawców z rozliczonymi wysyłkami. Dla v1 celowo konserwatywnie: żywy `keepOpen`, nierozliczone dziecko lub niepełna wiedza o potomkach nie zwalnia przydziału. Koordynator parkujący zadanie przekazuje blokadę i kończy lub bezpiecznie zamyka swoje bezczynne dzieci; rodzic doprowadza do potwierdzonego zamknięcia koordynatora. Sesji zarządzanej przez użytkownika nie zamykać bez zgody. Jeśli nie można bezpiecznie zaparkować drzewa, panel podaje właściciela nierozliczonego zasobu. Przy limicie 1 oznacza to realną blokadę miejsca, nie zależność merytoryczną. Nie zapewniać dalszej równoległości kosztem fałszywego zwolnienia. Samo `blocked`, `accepted`, abort-request, upływ czasu, zniknięcie panelu lub brak wpisu OS nie wystarczają. Gdy bieżący runtime nie dostarcza dowodu zamknięcia drzewa, dodać skorelowane rozliczenie potomków przez ich bezpośredniego właściciela **przed dopuszczeniem współdzielenia limitu**; nie zastępować dowodu odczytem drzewa historii.

### Rozliczenie rezerwacji i korekty — przypadki graniczne

- Rezerwacja ma klucz `(planId,taskId,attemptId)` i fazę `reserved` (brak zamiaru wysyłki), `dispatched`, `uncertain` lub `released`. Trzy pierwsze zużywają slot. Faza jest zmieniana tylko przy zgodnej rewizji i dowodzie z runtime; `released` jest historyczna, nie usuwać rekordu. Gdy plan i manifest zapisują się osobno, po awarii przyjąć najostrożniejszą wersję zgodną z oboma zapisami. Brak manifestu sam w sobie nie stanowi dowodu braku wysyłki.
- Dodać `plan_update` / `releaseReservation` z `{action,planId,taskId,attemptId,reason}`. Rodzic może rozliczyć rezerwację wyłącznie po spełnieniu warunku zwolnienia z §4. Sprawdzić go pod tą samą ochroną co dispatch; zamknąć możliwość nowego startu na starym przydziale. Duplikat nie zwalnia kolejnego miejsca. Dla `reserved` bez rozpoczętej wysyłki i `in_progress` polecenie atomowo przeprowadza zadanie do `blocked`, tak by rodzic mógł świadomie wybrać retry zamiast pozostawić nieużywalną próbę. Dla zarezerwowanego zadania, które właśnie przestało spełniać zależności, widok podaje `decision / parent / release_reservation`, a nie `dispatch_bound`. Dla zakończonego zadania z potwierdzoną możliwością zwolnienia podaje tę samą akcję przed `closed`. W pozostałych stanach zachować także informację o rezerwacji w `reasons`.
- Limit napraw dotyczy **zleceń naprawczych po review**, nie wszystkich resume. Dla trybu kolejki rodzic rejestruje decyzję poprawy przed dispatch: identyfikator decyzji, ID próby/uwagi review, wersja ocenionego artefaktu, przesłanka, numer rundy. Koordynator prowadzi decyzję dla własnego dziecka w swojej autoryzowanej ścieżce; agregat trwale przypisuje ją do zadania nadrzędnego. Ten sam identyfikator nie zwiększa licznika i nie wysyła ponownie polecenia. Kontynuacja po odmowie bezpieczeństwa nie jest naprawą techniczną. Brak danych legacy nie uprawnia do zgadywania zużytego limitu.
- Gotowość nie jest obietnicą niezmienności zależności. Unieważnienie akceptacji po starcie konsumenta nie przerywa procesu siłą: rodzic oznacza jego wynik do ponownej oceny; przed `accept` w trybie kolejki sprawdzić, że wymagane zależności są zaakceptowane w wersjach użytych przez konsumenta. Jeśli nie — odmówić i wymagać ponownej weryfikacji. Rewizja całego planu (np. zmiana innego zadania) nie jest wersją artefaktu.

## 5. Obowiązki agentów i przepływ informacji

- Rodzic na początku pracy, po wyniku, decyzji użytkownika, zakończeniu oceny lub rozliczeniu blokady sprawdza `nextActions` na najbliższej aktywnej turze. Zleca pierwsze gotowe zadanie i ponownie czyta stan, aż brak miejsca/kandydata. Nie czeka na zakończenie A przed zleceniem niezależnego C. Nie stosuje pętli sprawdzającej stan, gdy brak kandydata. Przy braku gotowych: jedna zbiorcza informacja o potrzebnych decyzjach, nie nowa tura per wpis.
- Koordynator lokalnie obsługuje review i poprawki własnego workera; nie wybudza głównego agenta obserwacjami. Eskaluje decyzję przekraczającą zakres albo niemożność kontynuacji; podaje `taskId`, przeszkodę, dostępne dowody, bezpieczną opcję i skutek braku odpowiedzi. W sytuacji „worker pyta koordynatora” ruch należy do koordynatora; nie wolno pozostawić obydwu stron w oczekiwaniu na siebie.
- Panel korzysta z tej samej funkcji oceny co bramka startu. Odświeżenie, heartbeat i upływ czasu nie emitują `steer`. Wynik/help/error budzi tylko właściwego bezpośredniego rodzica istniejącą ścieżką; brak nowego protokołu czatu. Nie importować pełnych rozmów dzieci do kontekstu głównego agenta. Widok „Następny ruch” nie zastępuje historii ani raportu odzyskiwania.

## 6. Obsługa błędów — polityka obowiązkowa

| `code` | Decyzja; zabronione zachowanie |
|---|---|
| `repair_failed` | Zachować częściowe zmiany i niezaliczone kryteria. Poprawka tylko z nowym dowodem/hipotezą; maks. 3 rundy po review na tę samą definicję zadania, także po wznowieniu lub zmianie wykonawcy. Liczyć decyzję o zleceniu poprawki raz, przed wysyłką; nie liczyć testu ani duplikatu dostawy. Ponowić testy i niezależne review na tej samej wersji. Bez postępu lub po limicie zatrzymać naprawę, nie obniżać kryteriów. |
| `provider_restriction` | Rozróżnić ostrzeżenie od odmowy. Zachować bezpieczny wynik częściowy, nie uznawać samego słowa „security” w logu za odmowę. Nie przekazywać zakwestionowanej operacji innemu modelowi ani nie przepisywać promptu w celu obejścia. Rzeczywiście odrębny defensywny zakres dopuszczalny; zmienione kryteria zatwierdza użytkownik. Nie twierdzić, że użytkownik naruszył zasady. |
| `infrastructure` | Bez automatycznych powtórzeń wykonania w v1. Przy potwierdzonym braku startu rodzic może jawnie zlecić nową próbę po usunięciu przyczyny; gdy efekty nieznane, stosować `uncertain_effects`. Nie zmieniać automatycznie providera/kosztu. Odrębne istniejące ograniczone retry dostarczenia nie uruchamia wykonawcy. |
| `missing_capability` | Wskazać brak narzędzia/uprawnienia; nie poszerzać profilu, nie sterować terminalem zastępczo. Świeża sesja tylko po rozliczeniu poprzedniej i jawnej decyzji. |
| `uncertain_effects` | Timeout transportu, utrata rodzica, niepotwierdzone przerwanie: zatrzymać powtórzenie konfliktującej pracy, utrzymać rezerwację, wskazać recovery/audit i granicę weryfikacji. Brak opcji „force release” w v1. |
| `scope_decision` | Sprzeczne wymagania, konieczna zmiana API/zakresu/kosztu: jedno pytanie do upoważnionej osoby, wskazanie zadań dotkniętych i niezależnych. Brak odpowiedzi nie oznacza zgody. |
| `invalid_result` | Exit bez raportu, brak dowodu lub niezgodne wersje testu i review: rodzic sprawdza artefakty; bez akceptacji i automatycznego rollbacku. |
| `unknown` | Dane legacy/niejednoznaczne: bez automatycznego rozpoznawania na podstawie słów i bez retry; decyzja rodzica. |

Przy błędzie zapisu wstrzymać operacje wymagające niesprawnego magazynu, nie potwierdzać niezapisanych decyzji. Trwała pauza globalna tylko na jawne polecenie lub faktyczną niemożność bezpiecznego wykonania na poziomie całego planu. Stary wynik zachować przy pierwotnej próbie, nie odblokowywać nim nowej próby. Anulowanie celu nie jest rollbackiem ani dowodem zakończenia procesu.

## 7. Kolejność dostawy i odbiór

1. Ustalić docelową rewizję i stan prac nad kontrolą własnych dzieci; nie nadpisywać zmian z równoległej sesji. Najpierw testy istniejących kontraktów oraz czysty evaluator z tabelą stanów. Następnie wersjonowane metadane, rezerwacje, recovery i bramki rzeczywistych narzędzi. Dopiero potem UI, instrukcje agenta głównego i koordynatora, `CONTRACTS.md`, `docs/REFERENCE.md`. Nie ogłaszać trybu obsługiwanym po samym wdrożeniu widoku.
2. Każdy poniższy przypadek musi mieć deterministyczny test z kontrolowanym wykonawcą/transportem. Dla zakazanej operacji asercja dotyczy **liczby rzeczywistych wywołań transportu = 0**, nie jedynie etykiety panelu. Dla wyścigu: jeden dispatch, jedna rezerwacja. Sprawdzać też plan, właściciela, oczekiwaną akcję i powody.

| ID | Given / When → Then |
|---|---|

3. Uruchomić typecheck, lint, testy obszarowe i pełne testy jednostkowe. Oddzielnie wykonać realny scenariusz Pi/herdr: lokalna naprawa A, start niezależnego C przy dostępnym miejscu, brak startu zależnego B, powrót do A po decyzji. Zapisać wersję kodu, ustawienia limitu, identyfikatory prób i zwięzłe dowody; bez sekretów i prywatnych logów. Brak dostępu do live = „niezweryfikowane live”, nie sukces E2E. Review i testy muszą dotyczyć tej samej wersji.

**Definicja ukończenia:** dla każdego nieskończonego zadania da się wskazać właściciela następnego ruchu, warunek dalszej pracy i bezpieczne działanie albo jawny brak bezpiecznego działania; żaden odczyt, błąd ani restart nie stanowi dorozumianej zgody na start, retry lub akceptację. Niezależna praca postępuje przy dostępnych zasobach, nie kosztem dublowania niepewnego wykonania.
